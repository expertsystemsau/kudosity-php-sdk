# Handoff: Kudosity 2.0, Phases 1–4 merged and pushed, Phase 5 next

## Goal

Upgrade this PHP SDK from the TransmitSMS V1 API to Kudosity's V2 API, shipping as a 2.0. Kudosity runs **two APIs under one account** and V2 cannot replace V1, so the SDK is dual-API: V2 is the default surface, V1 is retained for the capabilities that exist nowhere else.

| | Base URL | Auth | Covers |
|---|---|---|---|
| **V1** | `api.transmitsms.com` | HTTP Basic, key and secret | contact lists, bulk and scheduled sends, reporting, balance |
| **V2** | `api.transmitmessage.com` | `x-api-key` header, API key only | single-recipient SMS, MMS, WhatsApp, RCS, webhooks, senders |

**V2 never uses the secret. V1 always needs both.** Both hostnames are real and neither is a Kudosity domain — see Failed Approaches.

Six phases, specced in `docs/superpowers/specs/2026-08-04-kudosity-v2-migration-design.md`. Each phase's plan is written just before it runs.

## Failed Approaches (Don't Repeat These)

**A brand sweep using `\btransmitsms\b` silently corrupted the V1 hostname.** In `api.transmitsms.com` the dots are word boundaries, so `\b` matched *inside* the hostname and rewrote `KudosityV1Connector::BASE_URL` to a non-existent `https://api.kudosity.com`. The grep policing the sweep could not see it, because the corruption destroyed the string being searched for. **Any sweep needs a negative check for the corrupted form** — and that negative check needs the *same* exclusions as the positive one, or it fires on six prose hits in `HANDOFF.md` and `.ai-skills/handoffs/*`, which narrate the bug by name.

**A `\->sms\(\)` sweep cannot see a static facade call.** Three rounds reported "clean" while `README.md:193` held `Kudosity::sms()`. Use `'\->sms\(\)|::sms\(\)|\bSmsResource\b'`, and never accept the word "clean" — ask for the literal output.

**Removed public symbols went missing from `rename-map.json` in Phases 1 and 2.** Phases 3 and 4's audits both came back clean because the step exists. **Keep it in every phase plan.** Phase 4's audit did surface one line (`MAX_MESSAGE_REF_LENGTH`) — verify before acting: it moved to a trait and is still reachable on all four classes, and it postdates 1.x, so it was not a removal at all.

**`removed` map entries cannot flag a class.** The flagger appends `(` before matching, so it never matches a `use`, a `::class`, or a type hint. A removed **class** goes in `classes` with a real target; only methods belong in `removed`.

**Symlinking `vendor/` into a git worktree does not work here.** Composer's `autoload_psr4.php` resolves `$baseDir` back through the symlink, so `vendor/bin/pest` runs the tracked tree's code and a deliberate regression appears to pass. Work on a branch in the primary checkout.

**Regexes anchored `'/^…$/'` without `/D` have a newline hole.** Fixed everywhere now; a sweep returns only the two anchored patterns in `PhoneNumber.php`, and `:251` correctly needs no `/D`.

**Three tests that could not fail shipped inside Phase 3.** The discipline that catches them: revert the behaviour, watch the test fail, restore, put the transcript in the report. Phase 4 ran mutations on every task and found **two real coverage gaps** that way (a trimmed `SourceMessage::message`, and `verify()`'s empty-secret guard).

**Two mutation-testing failure modes that look exactly like a surviving mutation.** Phase 4 hit both: (1) a `perl -0pi -e` pattern that silently no-oped — **always verify the file actually changed**; (2) an "equivalent refactor" masquerading as a mutation — `array_filter()` without a callback still drops `[]`, because an empty array is falsy. A mutation that does not change behaviour proves nothing about the test.

**Some invariants cannot be mutation-tested at all.** `hash_equals` → `===` in `SignedMessageRef` passes every test, because the difference is timing rather than result. It is recorded as an invariant in the class docblock instead. Do not add a test that pretends to cover it.

**Do not invent a DTO or a request body for an undocumented shape.** But do not stop at "undocumented" either — **ask the API**. See Code Context: posting `{}` makes it name its own required fields.

**Do not predict exact test counts in a plan.** Phase 3's plan double-counted a dataset's own `it()` block and every later prediction inherited the error.

## Key Decisions

| Decision | Rationale |
|---|---|
| Dual-API, V2 primary | V2 has no equivalent for contact lists, bulk/multi-recipient sends, scheduling, reporting or balance. |
| API hostnames keep their real values | Kudosity renamed neither. Both must survive every sweep. |
| `sms()` is V2 single-recipient only | `POST /v2/sms` takes one recipient and cannot schedule. |
| GET readers extend `KudosityV2Request`, writers `KudosityV2BodyRequest` | A body on a GET — even `[]` — is stripped or rejected by some gateways. |
| One `MessageStatus` enum as the union of three vocabularies | The lists disagree and will grow; all resolve via `fromApi()` to `Unknown`. |
| Every V2 enum is open, resolving unknowns to `Unknown` | A client reading its own history must not break because Kudosity added a value. |
| **`UnknownEvent` is returned, never thrown** | A receiver does not choose what it is sent. A 500 on a new event type reads as a dead endpoint from Kudosity's side, which triggers a retry into the same 500. `raw` makes it survivable. |
| **`StatusPrecedence` is a rank, not a terminal check** | `MessageStatus::isTerminal()` is true for both `DELIVERED` and `READ`, so "never overwrite a terminal status" drops an RCS read receipt that legitimately follows delivery. |
| **`SoftBounce` ranks below the final outcomes; `Other` ranks with them** | A soft bounce means the handset was off, so a later `DELIVERED` is the truth. `Other` is the carrier's terminal catch-all and carries no lifecycle position, so ranking it low would let a stale `SENT` overwrite it. |
| **Equal status ranks return false** | Deliveries are at-least-once; a consumer counting state changes must not double-count one event. |
| **`SignedMessageRef` protects correlation, not the payload** | Stated in the docblock, because a reader will otherwise assume it authenticates the delivery. |
| **Signed refs parse from the LAST colon** | Real refs are composite (`order-9931:cust-4471`); `explode(':')[0]` truncates the entity while looking plausible. |
| **`verify()` returns null for every failure alike** | Distinguishing wrong-secret from tampered-entity hands an attacker an oracle. Returns null rather than throwing, because a forged POST is expected input on a public endpoint. |
| **The SDK rejects an `http://` webhook URL although the API accepts one** | Deliveries carry message text and phone numbers and are unsigned, so a plaintext endpoint is readable and forgeable in transit. **This is the one place the SDK is deliberately stricter than the platform — flagged for review.** `WebhookData::isSecure()` reports on registrations that already exist. |
| **`GET /v2/webhook/{id}` implemented as a real endpoint read** | It exists (200), despite being absent from the vendored skill. The plan's `find()`-over-`all()` fallback was not needed. |
| **`SenderRegistrationData` reads the status from any `details` key** | The skill documents `details.alphanumeric.status`, but the API only accepts `type: PERSONAL_MOBILE_NUMBER`. Hardcoding either would be wrong for the other. |
| **`isReadyToUse()` is false for `Unknown`** | Defaulting an unrecognised registry state to sendable is how a half-provisioned sender reaches production. |
| **`V2PagedPaginator` reads two total locations** | Senders is page-based but names its total `meta.pagination.total_count`. A third paginator for one renamed field was not worth it. |
| **`ListSenderRegistrationsRequest` has no `createDtoFromResponse()`** | The paginator reads items off the JSON and never calls `.dto()`, so it would be unreachable — same reasoning as `ListWhatsAppRequest`. |
| PHP floor stays `^8.2` | User's call, despite the toolchain needing 8.3+. |
| **Phase 5: webhook receiver authenticates by unguessable URL** | There is no signature to verify — confirmed empirically, twice. |

### Make the API tell you its own schema

The single most useful technique this phase produced. When a V2 endpoint's request body is undocumented, **do not infer wire names** — an unsupported parameter is silently ignored, so the call looks successful and does nothing. Post an empty body and read the RFC 9457 `issues[]`:

```bash
curl -s -X POST "https://api.transmitmessage.com/v2/senders/registrations" \
  -H "x-api-key: $KEY" -H 'Content-Type: application/json' -d '{}'
# {"error":{"issues":[{"name":"sender","message":"sender is required"},
#                     {"name":"country",...},{"name":"type",...}]}}
```

Then post a deliberately **invalid** enum value to get the permitted set: `type must be one of: PERSONAL_MOBILE_NUMBER`, `method must be one of: SMS`. Every probe can only be rejected, so nothing is created — but check the account afterwards anyway.

### The two Phase 4 findings that change how you read the API

**Deliveries are at-least-once, and a stale status really does arrive after a newer one.** The `SENT` event was redelivered 60s later carrying its *original* timestamp, arriving **57s after `DELIVERED`**, byte-identical to the first. Nothing in the payload distinguishes the duplicate, so the guard can only compare against recorded state. Full timeline in the fixture README.

**A `LINK_HIT` is not evidence a human clicked.** The first hit arrived in the *same second* as `DELIVERED`, ~2s after the send — a messaging-app link preview. The human tap was the second hit, 16s later. `hits` is cumulative and counts machine fetches, so it is not an engagement metric. Also: `link_hit.url` is the original destination while `source_message.message` carries the **shortened** link.

### The senders endpoint is narrower than its name

`POST /v2/senders/registrations` accepts exactly one `type`: `PERSONAL_MOBILE_NUMBER`. It registers **a personal mobile**, verified by SMS code. Alphanumeric sender IDs, WhatsApp Business senders and RCS agents need Kudosity approval and never appear here — and a **leased virtual number is not a registration**, which is why this account sends fine and reports zero. **So Phase 4 did not unblock WhatsApp/RCS verification.** Use V1 `$k->numbers()` for leased numbers.

## Edge Cases & Error Handling

- **Handled:** both V2 envelope shapes; RFC 9457 with per-field `issues[]`; the plain `{"error": "..."}` body the webhook endpoints use; a non-JSON error body; the missing-secret case; a truncated or hostile webhook payload (missing section key, wrong type, malformed timestamp — all yield nulls rather than fatals); an unrecognised event type; a `webhooks` key that is not a list.
- **Deferred:** `paginationDirection()` is forwarded into the query unvalidated. Both V2 paginators' `getPageItems()` declare `array<int, mixed>` but return `mixed`.
- **Unverified by construction:** the sender registration *item* shape, and the success bodies of `register()` / the verification calls. All read defensively with `raw` retained.
